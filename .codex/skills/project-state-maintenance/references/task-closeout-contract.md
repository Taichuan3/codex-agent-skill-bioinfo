# Task closeout and bounded context

Use after an authorized material project write, including a failed run that changes a blocker. This is a closeout step, not permission to expand research, change global rules, migrate files, publish, or install. Pure reading produces no state-file writes.

## One owner, one delta

The main agent or explicitly assigned sole owner receives each worker's changed assets, actual status, evidence and unresolved questions. Only this owner writes shared GUIDE/PLAN/registries. Capture the original content hash; re-read and reconcile if it changes before writing. Do not overwrite concurrent user edits.

Ask only what this task changed:
- artifact path, version, module, consumer or candidate/current role;
- completed, failed or blocked work;
- key limitation, accepted decision or next step;
- durable scientific fact with evidence and author-acceptance state.

No delta means `unchanged` with one reason, not a fabricated update. Navigation changes matter even when scientific conclusions do not. File existence, a checksum or a successful command does not establish scientific acceptance.

## Minimum sequence

1. Validate the changed artifact and explicit dependencies only. Record gaps.
2. Update the existing scoped artifact registry and regenerate affected human views. No competing current registries. Unknown source/producer fields stay `pending`.
3. If the hot summary changes, use `project-guide-maintainer` for a local replacement, preserving caveats and acceptance. Cards link to the registry instead of copying full lists.
4. Append one concise task record to PLAN without a full read. GUIDE/PLAN coupling follows prepared/committed; do not add a second ordinary record for that change. Child documentation writes are part of closeout, not recursive tasks.
5. Verify affected links and scoped current roles. From root navigation find the changed figure/table, source and producer without chat or PLAN. Report `updated`, `unchanged` or `blocked` for GUIDE, navigation and PLAN. If blocked, identify the evidence/permission or decision owner needed.

No move is required to expose existing artifacts. New writers declare stable module/output roots before running; dates identify runs, not the only route to current work. Promoting a candidate follows user authority; technical completion does not confer scientific acceptance.

## Context budget

Read project rules, the short GUIDE if relevant, and only the selected module/consumer. GUIDE defaults to 1,000–2,000 characters; above 3,000 characters or 80 lines is a compression warning. Never trim protected caveats automatically. Above 6,000 characters or 120 lines is a legacy-limit breach requiring repair or a project exception. Retained as-of background is not another current GUIDE.

`verify_project_handoff.py` checks an explicit GUIDE/TSV and local path/hash metadata, without networking or writes. It cannot prove science, author approval, reproduction or complete source coverage. Review warnings and test the human route separately. Do not scan all data for a small closeout.

## Behavioral acceptance

- Path-only revisions update current routes without inventing findings.
- Failed runs update blockers, not success claims.
- No-change/read-only questions create no empty logs.
- Workers return deltas; one owner merges shared state.
- A new session finds current assets without cold history.
- Repeated updates replace old state and preserve caveats and budgets.
